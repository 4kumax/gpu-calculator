# GPU Calculator

Калькулятор GPU-инфраструктуры: подбор модели и профиля запуска под задачи, оценка памяти и нагрузки, сравнение покупки и аренды, сохранение воспроизводимых сценариев.

## Запуск

Node.js 22 или новее.

```bash
npm ci
npm run dev
```

Калькулятор: `http://localhost:3000`. Каталоги и допущения: `/settings`.

```bash
npm test
npm run typecheck
npm run format:check
npm run build
npm start
```

CI выполняет эти проверки на Node.js 22 и проверяет общий каталог на отдельном PostgreSQL 16.

## Как считается конфигурация

1. Выбранные задачи задают минимальное качество, контекст и обязательные возможности. Неизвестные и выключенные идентификаторы задач вызывают понятную ошибку.
2. Для каждой модели рассматриваются её активные профили запуска. При фиксированном GPU подбор и альтернативы используют этот ускоритель.
3. Память включает веса с запасом, KV-кэш всех одновременных запросов и рабочую память GPU. Длина входа и ответа влияет на KV-кэш. Вход `0` означает использование требования контекста выбранных задач.
4. Ёмкость экземпляра ограничивается памятью, плановой параллельностью и условиями измерения. Количество экземпляров покрывает пик после применения доли нагрузки, включая доли менее 1%.
5. Покупка округляется до целых серверных узлов. N+1 добавляет один резервный узел. Память резерва и незадействованных GPU не выдаётся за рабочую ёмкость.

Профиль хранит модель, GPU, движок и версию, формат весов, число GPU, tensor/pipeline parallelism, память на 1 000 токенов запроса, рабочую память на GPU и предельную нагрузку. Дополнительные измерения содержат длины входа/ответа, параллельность, задержку первого токена и скорость ответа.

Встроенные профили имеют статус **плановых**. Начальные коэффициенты KV-кэша `0,125 ГБ / 1000 токенов / запрос` и рабочей памяти `1 ГБ / GPU` — единые редактируемые допущения, а не характеристики архитектуры. Их необходимо заменить измерениями конкретного движка и чекпоинта. Наращивание GPU из-за памяти даёт предварительный расчёт с предупреждением о новой топологии.

Измеренная производительность применяется только в границах указанной нагрузки, оборудования и срока актуальности источника. Выход за эти условия, включая масштабирование на несколько реплик, понижает статус подтверждения. Если задана целевая задержка или скорость, отсутствие применимого измерения отмечается как невыполненное требование. Базовые принципы памяти и параллелизма описаны в [документации vLLM](https://docs.vllm.ai/en/stable/configuration/optimization/).

## Качество и источники

Класс модели в каталоге является экспертной оценкой. В разделе «Испытания качества» можно добавить результаты для пары модель/задача: датасет, размер выборки, класс, долю верных ответов, ошибки извлечения и успешность вызовов инструментов. Актуальная измеренная оценка участвует в проверке требований и ранжировании. Публичная карточка модели не подтверждает качество на корпоративных документах. Приложение не создаёт вымышленные результаты испытаний.

Характеристики модели, профиль запуска, испытание качества, цена покупки и тариф аренды имеют отдельные источники и даты. Неподтверждённые тарифы из старого каталога перенесены как инженерные оценки. Источники, условия цен и предупреждения об устаревании видны в деталях расчёта. Настройка срока актуальности применяется к ценам и измерениям.

## Экономика

TCO покупки состоит из оборудования, ввода, резерва бюджета, поддержки, энергии, размещения, сети/хранилища и эксплуатации за вычетом остаточной стоимости. TCO аренды отдельно раскрывает рабочие GPU, резерв, сервисную надбавку, сеть/хранилище и эксплуатацию.

- **GPU по часам:** оплата рабочих GPU за часы нагрузки.
- **Выделенные узлы:** оплата всех GPU рабочих узлов за 730 часов ежемесячно. Стоимость выводится из GPU-часового тарифа; отдельное предложение аренды узла требуется подтвердить у поставщика.
- **Резерв:** постоянная оплата либо только в часы нагрузки; для выделенных узлов резерв всегда оплачивается за 730 часов.

Порог покупки различает выгоду выше или ниже определённой загрузки, выгоду при любой загрузке, отсутствие выгоды и равенство. График показывает начальные вложения в момент 0, текущие расходы и остаточную стоимость в конце горизонта. Дисконтирование не применяется.

Чувствительность считается для фиксированной выбранной конфигурации: цены покупки/аренды меняются на ±20%, часы — на ±25% в пределах месяца. Это сопоставление условий, а не вероятностный прогноз. Стоимость других маршрутов при доле нагрузки меньше 100% в расчёт не включена.

## Сценарии

Текущие параметры восстанавливаются после перехода в настройки и перезагрузки. Можно сохранить до 20 именованных сценариев и сравнить до четырёх одновременно.

Каждый сценарий содержит копию каталога, параметры, дату расчёта и версию алгоритма. Экспорт JSON дополнительно содержит полный результат; импорт проверяет исходные данные и пересчитывает результат, не доверяя чужим итоговым цифрам. Открытие сценария использует его собственные цены; переход на текущий каталог выполняется отдельной кнопкой. Файлы несовместимой версии алгоритма не выдаются за воспроизведённые расчёты.

При повреждённом хранилище данные не перезаписываются автоматически: доступен экспорт исходного содержимого и восстановление с резервной копией.

## Настройки и миграция

Схема каталога — **v3**. Сохранённая конфигурация v2 проходит полную проверку и мигрирует с сохранением пользовательских численных значений. Схема, версия встроенного каталога и последовательная ревизия сохранения разделены.

Редактор предоставляет:

- подписанные поля и флажки возможностей;
- отдельные редакторы моделей, профилей, качества, цен, правил и допущений;
- автоматическое сохранение черновика в пределах вкладки;
- сравнение импорта, встроенного каталога и исторических ревизий перед применением;
- защиту от перезаписи изменений из другой вкладки и перенос своих правок на новую ревизию;
- обработку ошибок и переполнения хранилища, экспорт для восстановления.

Локальная история содержит последние 15 записей. Восстановление старых данных создаёт новую ревизию, а не откатывает её номер. Обновление встроенного каталога не перезаписывает пользовательские настройки без применения изменений в редакторе.

Черновик сохраняется при переходах и перезагрузке страницы, но удаляется при закрытии вкладки. Перед закрытием сохраните изменения в каталог или экспортируйте их; при несохранённых правках приложение показывает предупреждение браузера.

## Общий каталог PostgreSQL

Без `DATABASE_URL` приложение работает локально. Для совместного режима нужны отдельная PostgreSQL-база и серверные переменные из `.env.example`:

```bash
cp .env.example .env.local
```

Заполните `DATABASE_URL`, `CATALOG_EDITOR_TOKEN`, `CATALOG_VIEWER_TOKEN` и `CATALOG_SESSION_SECRET`. Три секрета должны отличаться и содержать минимум 32 символа. Для каждого можно отдельно выполнить `openssl rand -hex 32`. Секреты не должны иметь префикс `NEXT_PUBLIC_` и не должны попадать в git.

В production используйте HTTPS и защищённое подключение к PostgreSQL. При reverse proxy укажите `CATALOG_ALLOWED_ORIGIN` с внешним origin приложения. Неполная серверная конфигурация блокирует общий режим с явной ошибкой; запись не переключается молча в локальное хранилище.

Первое авторизованное чтение создаёт таблицы и ограничения истории. До первой публикации общий каталог имеет ревизию 0. Редактор публикует его явным сохранением; читатель может только просматривать. Сессии хранятся в подписанной HttpOnly cookie, права и Origin проверяются на сервере. Смена ключа роли или секрета сессии аннулирует соответствующие сессии.

**Ключи доступа идентифицируют роль, а не отдельного сотрудника.** Журнал использует `CATALOG_EDITOR_NAME` как имя автора роли. Персональные учётные записи и SSO не входят в этот механизм.

Публикация и снимок истории записываются одной транзакцией с проверкой ожидаемой ревизии. Конкурирующая запись получает HTTP 409. PostgreSQL запрещает изменение и удаление записей истории через UPDATE/DELETE/TRUNCATE. Интерфейс показывает последние 100 ревизий; отдельные снимки доступны по номеру.

API:

| Метод и путь                         | Назначение                                                  |
| ------------------------------------ | ----------------------------------------------------------- |
| `GET /api/catalog`                   | Режим, сессия, текущая конфигурация и история               |
| `POST /api/catalog/session`          | Вход по ключу роли                                          |
| `DELETE /api/catalog/session`        | Выход                                                       |
| `PUT /api/catalog`                   | Публикация `{config, expectedRevision, message}` редактором |
| `GET /api/catalog/history`           | История                                                     |
| `GET /api/catalog/history/:revision` | Снимок ревизии                                              |

Проект совместим с обычным развёртыванием Next.js, в том числе Vercel. Для общего режима используйте внешнюю PostgreSQL-базу; файловая система сервера для хранения каталога не используется.

## Проверки

Тесты покрывают подбор, память, измеренные ограничения, целевые оценки качества, TCO и его границы, отдельные источники, импорт/миграцию, локальные конфликты и восстановление, DOM-сценарии, роли, сессии, API и историю.

`pg-mem` проверяет SQL и базовые операции локально. Для настоящих гарантий PostgreSQL — конкурентного первого сохранения, отката транзакции и неизменяемости истории — задайте `TEST_DATABASE_URL` на отдельную тестовую базу на `localhost`/`127.0.0.1`, имя которой содержит `test`. Тест создаёт и удаляет только собственную временную схему. Без переменной эта проверка явно пропускается; CI запускает её с сервисом PostgreSQL.
