# GPU Calculator

Планирование GPU-инфраструктуры для руководителя: готовые бизнес-сценарии, сравнение моделей и оборудования, полная стоимость покупки и аренды на одинаковом горизонте. Технические настройки находятся на странице **«Параметры»** (`/settings`).

## Запуск и проверки

Node.js 22 или новее.

```bash
npm ci
npm run dev
```

Приложение: `http://localhost:3000`.

```bash
npm test
npm run typecheck
npm run format:check
npm run build
npm start
```

CI выполняет проверки на Node.js 22 и запускает интеграционный тест общего каталога с PostgreSQL 16.

## Интерфейс и сценарии

На главной странице достаточно выбрать сценарий и сравнить варианты. Встроенные значения — редактируемые предположения для планирования, а не замеры пользовательской нагрузки:

| Сценарий              | Назначение                             | Запросов одновременно | Вход / ответ, токенов | Часов в месяц | Горизонт | Резерв   |
| --------------------- | -------------------------------------- | --------------------: | --------------------: | ------------: | -------: | -------- |
| Пилот ИИ-ассистента   | Поиск и подготовка ответов             |                     4 |           4096 / 1024 |           160 |    1 год | Нет      |
| Работа с документами  | Договоры, извлечение данных, сводки    |                     8 |          16384 / 2048 |           360 |   3 года | Нет      |
| Аналитика и агенты    | Сопоставление источников и инструменты |                     4 |          32768 / 4096 |           360 |   3 года | Нет      |
| Корпоративный масштаб | Постоянный доступ подразделений        |                    32 |           8192 / 2048 |           730 |   3 года | N+1 узел |

В каждом сценарии заранее заданы задачи, модели/GPU для начального выбора, приоритет, нагрузка, длина запросов, требования к скорости, срок, резерв и способ оплаты аренды. Названия, описание и все параметры редактируются в **«Параметры → Сценарии»**; там же выбирается сценарий первого открытия. Цены, профили запуска и общие финансовые допущения изменяются в остальных разделах параметров.

Карточка решения показывает выбранную конфигурацию, количество рабочих GPU и оборудования к покупке, TCO покупки/аренды и разницу. Таблица **«Модели»** сначала показывает до пяти вариантов, включая рекомендуемый и выбранный; кнопка раскрывает весь список. Таблица **«GPU»** показывает все активные типы ускорителей для выбранной модели: количество GPU, цену сервера, долю цены на GPU, тариф GPU-часа и полные расходы. Доля цены сервера не является отдельным предложением продажи карты. Для неподтверждённых сочетаний доступны причины ограничений; они не становятся рекомендацией только потому, что веса помещаются в память.

Технические основания, источники, состав расходов и чувствительность раскрываются по запросу. Выбор сценария и варианта восстанавливается после перезагрузки.

## Количество GPU

Расчёт разделяет четыре разных величины: нижнюю границу размещения весов, память одного запроса, размер экземпляра по профилю запуска и число экземпляров для заданной нагрузки. Затем покупка округляется до целых серверов; N+1 добавляет один резервный узел. Рабочая память не включает резерв и незадействованные GPU.

- **Веса:** используется размер тензоров чекпоинта, если он указан; иначе — общее число параметров × битность / 8. Для MoE требуются все размещённые веса, включая неактивных экспертов. Число активных параметров не заменяет размер модели.
- **Нагрузка:** KV-кэш зависит от фактической длины входа и ответа и параллельности. Требование задачи к максимальному контексту проверяет возможности модели. Оно не задаёт длину каждого запроса. Для старого входа `0` или отсутствующего значения используется `assumptions.defaultInputTokens` (8192); незаданный ответ — `defaultOutputTokens` (1024).
- **Профиль:** учитываются доступная память, запас для весов, workspace и ограничение параллельности. Размер существующего профиля не увеличивается автоматически: если даже один запрос не помещается, требуется отдельный профиль с допустимой топологией. Размножение неработоспособного экземпляра не исправляет нехватку памяти.
- **Сочетание без профиля:** рассчитывается условная оценка памяти с учётом пакетной обработки и копий весов. Она не подтверждает поддержку движка, формата, межсоединения или производительность и исключена из рекомендаций.

Встроенные профили предварительные. Общие коэффициенты KV-кэша `0,125 ГБ / 1000 токенов / запрос` и workspace `1 ГБ / GPU` редактируются и не являются архитектурными характеристиками. Измеренная производительность применима только в пределах нагрузки, оборудования, формата весов и актуальности источника. Несколько реплик или выход за измеренные условия требуют новой проверки. Требования к задержке первого токена и скорости без применимого измерения считаются неподтверждёнными.

### Почему раньше Kimi показывал 24 GPU

На прежнем экране задача с контекстом 1 млн токенов при входе `0` превращалась в запрос длиной 1 млн токенов. Вместе с общим коэффициентом KV это давало около 125 ГБ на запрос. После прежней оценки весов на одном профиле из 8 GB300 оставалось место для трёх запросов; пик 8 запросов превращался в `ceil(8 / 3) = 3` экземпляра, то есть **24 GPU**. Это был результат связанных допущений, а не опубликованный минимум Kimi.

Теперь длина запроса задаётся сценарием. Для Kimi K3 размер тензоров смешанного чекпоинта уточнён до **1560,860324864 ГБ** по `metadata.total_size` [официального индекса Hugging Face](https://huggingface.co/moonshotai/Kimi-K3/raw/main/model.safetensors.index.json). Это размер данных весов, а не измерение VRAM работающего сервера. Нижняя граница только по весам на 288-ГБ GPU — 6 GPU; она не определяет допустимую топологию запуска.

[Публичный предварительный рецепт vLLM](https://recipes.vllm.ai/moonshotai/Kimi-K3) указывает минимум **8 × GB300** для одного экземпляра. В каталоге сохранён этот профиль: при входе 8192, ответе 1024 и пике 8 запросов он даёт предварительную оценку одного экземпляра. Это не универсальное требование «всегда 8 GPU». Kimi использует гибридные KDA/MLA-состояния; общий коэффициент KV не заменяет модельный расчёт и нагрузочный тест. Увеличение нагрузки или контекста может изменить число экземпляров либо сделать профиль непригодным.

## Качество, цены и экономика

Класс качества модели — экспертная оценка. Актуальные результаты испытаний для пары модель/задача участвуют в проверке требований и ранжировании. Публичная карточка модели не подтверждает качество на корпоративных документах. Приложение не создаёт вымышленные результаты испытаний.

Характеристики, профиль, испытания, покупка и аренда имеют отдельные источники и даты. Неподтверждённые тарифы старого каталога остаются инженерными оценками. Срок актуальности применяется к ценам и измерениям.

TCO покупки включает оборудование, ввод, резерв бюджета, поддержку, энергию, размещение, сеть/хранилище и эксплуатацию за вычетом остаточной стоимости. TCO аренды включает рабочее оборудование, резерв, сервисную надбавку, сеть/хранилище и эксплуатацию. GPU можно оплачивать по часам нагрузки; выделенные узлы оплачиваются целиком за 730 часов в месяц. Стоимость выделенного узла выводится из GPU-часового тарифа и требует подтверждения поставщика. Резерв оплачивается постоянно либо в часы нагрузки; для выделенных узлов — постоянно.

График учитывает начальные вложения, текущие расходы и остаточную стоимость в конце срока. Дисконтирование не применяется. Чувствительность меняет цены на ±20%, часы на ±25% для фиксированной конфигурации. Это сравнение условий, а не вероятностный прогноз. Стоимость других маршрутов при доле нагрузки менее 100% не включена.

## Снимки и миграция

Можно сохранить до 20 именованных снимков и сравнить до четырёх. Каждый содержит собственные параметры, копию каталога с ценами, дату и версию алгоритма. JSON-экспорт дополнительно содержит результат; импорт проверяет исходные данные и заново считает итог. Открытие снимка использует его цены; возврат к актуальным сценариям выполняется отдельно.

Версия алгоритма — **4.0.0**, схема каталога — **v4**. Каталоги v2/v3 проходят проверку и мигрируют с сохранением пользовательских цен, характеристик и профилей; добавляются готовые сценарии и явные значения нагрузки. Только неизменённая прежняя запись встроенного Kimi получает уточнённый размер чекпоинта с предупреждением. Пользовательские размеры, форматы и источники сохраняются.

Снимки алгоритма 3.0.0 не выдаются за воспроизведённые текущим кодом. После явного выбора пересчёта создаётся новый сценарий с новым ID и датой; исходный импортированный файл не меняется. При пересчёте старой библиотеки сначала сохраняется отдельная резервная копия исходного JSON, затем заменяется активный список. Повреждённые данные не перезаписываются автоматически: доступны экспорт и восстановление с копией.

Редактор показывает различия перед импортом, обновлением встроенного каталога и восстановлением истории. Конфликты между вкладками требуют переноса своих изменений на актуальную ревизию. Локальная история содержит последние 15 записей. Черновик восстанавливается при переходах и перезагрузке, но хранится только до закрытия вкладки: перед закрытием сохраните каталог или экспортируйте JSON.

## Общий каталог PostgreSQL

Без `DATABASE_URL` используется локальное хранилище браузера. Для совместного режима нужны отдельная PostgreSQL-база и серверные переменные из `.env.example`:

```bash
cp .env.example .env.local
```

Заполните `DATABASE_URL`, `CATALOG_EDITOR_TOKEN`, `CATALOG_VIEWER_TOKEN` и `CATALOG_SESSION_SECRET`. Три секрета должны отличаться и содержать минимум 32 символа; генерировать каждый можно командой `openssl rand -hex 32`. Они не должны иметь префикс `NEXT_PUBLIC_` или попадать в git. В production нужны HTTPS и защищённое подключение к базе; за reverse proxy укажите внешний `CATALOG_ALLOWED_ORIGIN`.

Первое авторизованное чтение создаёт таблицы и ограничения истории. До первой публикации ревизия равна 0; редактор публикует каталог явным сохранением. Читатель имеет доступ только к просмотру. Сессия хранится в подписанной HttpOnly cookie; сервер проверяет роль и Origin. Неполная конфигурация или ошибка сервера не переключает запись молча в локальный режим.

Ключи идентифицируют **роль, а не сотрудника**. Журнал использует `CATALOG_EDITOR_NAME` как имя роли; персональных учётных записей и SSO нет. Публикация и снимок истории записываются одной транзакцией с проверкой ожидаемой ревизии; конфликт возвращает HTTP 409. PostgreSQL запрещает UPDATE/DELETE/TRUNCATE истории. Интерфейс показывает последние 100 ревизий.

| Метод и путь                         | Назначение                                       |
| ------------------------------------ | ------------------------------------------------ |
| `GET /api/catalog`                   | Режим, сессия, конфигурация и история            |
| `POST /api/catalog/session`          | Вход по ключу роли                               |
| `DELETE /api/catalog/session`        | Выход                                            |
| `PUT /api/catalog`                   | Публикация `{config, expectedRevision, message}` |
| `GET /api/catalog/history`           | История                                          |
| `GET /api/catalog/history/:revision` | Снимок ревизии                                   |

Поддерживается обычное развёртывание Next.js, включая Vercel с внешней PostgreSQL. Файловая система сервера для каталога не используется.

Тесты покрывают память и подбор, матрицу сравнений, TCO, сценарии и миграцию, интерфейс, конфликты хранения, роли и API. `pg-mem` проверяет базовые SQL-операции. Для проверки конкурентной записи, отката и неизменяемости истории на настоящем PostgreSQL задайте `TEST_DATABASE_URL` на отдельную базу `localhost`/`127.0.0.1` с `test` в имени. Тест создаёт и удаляет собственную временную схему. Без переменной этот тест явно пропускается; CI запускает его с PostgreSQL.
